# ตรวจเทียบโจทย์ Off-Grid SOS & Nearby Share — 0.9.9+30

วันที่ 2 พฤศจิกายน 2569

## ขอบเขตและหลักฐาน

ตรวจโค้ด Flutter ใน lib, บริการ Bluetooth/foreground service ของ Android, โครงสร้าง SQL/migrations/Edge Functions ของ Supabase และชุดทดสอบใน test โดยเน้นเส้นทางแชท SOS local DB คิวซิงก์ ตัวตนและบทบาทกู้ภัย เอกสารนี้ไม่ใช่การรับรองว่าโค้ดไม่มีบั๊กทุกเส้นทาง และไม่ได้ตรวจฐานข้อมูล Supabase ที่ deploy จริงด้วยสิทธิ์สมาชิกในรอบนี้

หลักฐานล่าสุด: build/tests-v30.log ผ่าน 192 เคส, build/analyze-v30.log ไม่พบปัญหา, build/apk-v30.log ประกอบ Android release สำเร็จ ผลอัตโนมัติจำลอง transport/player จึงไม่แทนผลฮาร์ดแวร์สองหรือสามเครื่อง

## เทียบข้อกำหนด

| ข้อกำหนด | สิ่งที่มี | ข้อจำกัด/ผลที่ยังต้องยืนยัน |
|---|---|---|
| ติดต่อไม่มี cellular/hotspot/infrastructure | Nearby Connections และ Bluetooth RFCOMM โดยตรง | ไม่จำเป็นต้องใช้ router; Nearby บางโหมดต้องเปิดวิทยุ Wi-Fi และบริการตำแหน่ง Android แม้ไม่ต่อเน็ต |
| Device-to-device ติดตั้งแอปทั้งสองเครื่อง | transport และ protocol เดียวกันใน APK | ต้องอนุญาตสิทธิ์และเปิดแอป/บริการรับข้อความ; Bluetooth โดยตรงใช้ bonded devices ต้องจับคู่ในการตั้งค่า Android |
| แชทข้อความ | บันทึก local ก่อนส่ง มี ID เดิม ACK retry และ dedup | ต้องวัดรับส่งหลังล็อกจอจริง |
| รูป/วิดีโอ | คัดลอกไฟล์ในเครื่อง แบ่งชิ้น เข้ารหัส ตรวจ hash ก่อนรับสำเร็จ ส่งซ้ำต่อจากส่วนที่รับแล้ว | จำกัด D2D ไฟล์ละ 25 MiB; codec และความเร็วจริงบน OPPO/Galaxy ยังไม่ยืนยันรุ่น 30 |
| สมาชิก/คลาวด์ | Supabase Auth profiles ห้องข้อความ storage และ sync queue | สมัคร/รีเซ็ตรหัสผ่าน/เปลี่ยนสิทธิ์ต้องออนไลน์; สมาชิกเดิมใช้ local identity ออฟไลน์ได้ มี guest สำหรับเริ่มใช้งานออฟไลน์ |
| สมาร์ทโฟน | Android APK minSdk 24 | native offline transport รองรับ Android; ยังไม่ถือว่ารองรับ iPhone/TestFlight |
| เปิด/ปิด SOS แสดงสีแดงเครื่องอื่น | SOS revision/status propagation, discovery mode, current cases และ UI สีแดง | การแสดงจริงขึ้นกับ discovery/handshake และ permission ไม่ใช่เปิด Bluetooth แล้วเห็นทันทีโดยไม่ต้องมี transport |
| แตะผู้ขอความช่วยเหลือเข้าบทสนทนา | การ์ด SOS เชื่อม unified conversation | เริ่มส่งได้เมื่อมีเส้นทางถึงผู้รับหรือเก็บคิวไว้ |
| เปิด/ปิดกู้ภัย แสดงสีน้ำเงินเครื่องอื่น | signed role attestation + active rescue status + blue cards/badge | ต้องมีสิทธิ์ที่ยืนยันแล้ว ใบรับรอง offline มีอายุ 30 วัน; หมดอายุต้องต่อเน็ตเพื่อต่ออายุ ไม่ให้แสดงสิทธิ์ปลอม |
| SOS ข้อความสั้นและพิกัดล่าสุดออฟไลน์ | local SOS + prepared/cached/live GPS + publish บน mesh และอัปเดตพิกัดตาม revision | ถ้ายังไม่มี fix และไม่มีตำแหน่งเก่า จะส่ง SOS ก่อนโดยยังไม่มีพิกัด แล้วเพิ่มเมื่อ GPS มา ไม่สร้างพิกัดสมมติ |
| คิวและซิงก์เมื่อกลับออนไลน์ | local queue, retry, backoff/idempotency, cloud archive | ต้องยืนยัน HTTP/RLS/storage กับบัญชีจริงและไฟล์จริงรุ่นล่าสุด |
| ค้างส่ง/ส่งแล้ว/ซิงก์แล้ว | แชทมี delivery/ACK แยก cloud synced | หน้า SOS เน้น active และ cloud sync แต่ยังไม่มีสถานะรับ SOS รายเครื่องแบบ durable ACK ที่ครบเหมือนแชท จึงถือว่า UI การส่ง SOS ยังมีส่วนต้องทำให้ชัด |
| ทุกฟีเจอร์หลัก offline/local DB | Sembast stores, durable media, local identity, cached rescue history | ดาวน์โหลดสื่อคลาวด์ครั้งแรก/ยืนยันบัญชีใหม่/อนุมัติกู้ภัยใหม่ออฟไลน์ไม่ได้ เป็นงานออนไลน์แยกจากหลักแชท/SOS |
| ส่งต่อหลาย nodes | route discovery + encrypted routed text/media + SOS relay + dedup/tombstones | hop/TTL จำกัดเพื่อป้องกัน loop (routed private traffic สูงสุด 6; SOS broadcast เริ่ม TTL 3) ไม่ใช่เครือข่ายไม่จำกัด hop และยังต้องพิสูจน์ A-B-C ทางวิทยุจริง |
| ตัวอย่างอย่างน้อย 2 เครื่อง | มีภาพ/การทดลองผู้ใช้รุ่นก่อน และ simulation หลาย nodes | รุ่น 30 ยังต้องบันทึกผลจริง 2 เครื่อง; ภาพบั๊กจากรุ่นก่อนใช้ยืนยันว่ารุ่นล่าสุดผ่านไม่ได้ |

## สิ่งที่ขาด/ยังไม่พร้อมยืนยัน

1. หลักฐานทดลองรุ่น 30 บน 2 เครื่องโดยปิด data และไม่เชื่อม router/hotspot: ข้อความ รูป วิดีโอ ตำแหน่ง SOS สีแดง กู้ภัยสีน้ำเงินและเปิดแชทจากการ์ด
2. ทดลอง 3 เครื่อง A-B-C โดย A ติดต่อ C โดยตรงไม่ได้ ต้องผ่าน B ทดสอบทั้งข้อความ SOS และไฟล์ รวม B หลุดแล้วกลับมา
3. ทำสถานะส่ง SOS ให้แยก local saved / ส่งผ่านวิทยุ / ผู้รับ ACK / cloud synced ชัดเจน ปัจจุบันจำนวน broadcast ไม่ใช่หลักฐานผู้รับบันทึกและไม่ใช่การยืนยันรับเคสกู้ภัย
4. ผลความเร็ว/หน่วยความจำ/วิดีโอจริง/จอดับบนอุปกรณ์เป้าหมาย ยังไม่มี profiling รุ่น 30 ตัวเลข 192 tests ไม่ใช่ผล benchmark
5. ทวนฐานข้อมูล live ว่า migrations, RLS, storage policies และ Edge Functions ตรง repository ด้วยบัญชีจริง รอบนี้ตรวจได้เฉพาะโค้ดที่เก็บในโปรเจกต์
6. ความคาดหวัง “ทันที” ต้องตรวจเวลาจริง discovery+identity verification แยกจากรับ status บนลิงก์ที่มีอยู่แล้ว โหมด RFCOMM ไม่ใช่การค้นหาเครื่องแปลกหน้าโดยไม่จับคู่

## ส่วนที่ทำเพิ่มจากโจทย์

- โหมด guest ไม่ต้องสมัครก่อนใช้พื้นฐานออฟไลน์
- ส่งตำแหน่งในแชท แผนที่ OpenStreetMap ปทุมธานีติดตั้งในแอป ออฟไลน์ พร้อมแนวทาง/ทิศทางในแอป
- ถ่ายรูป/ถ่ายวิดีโอจากกล้องและกู้ไฟล์หลังกลับจาก camera activity
- SOS กดค้าง 3 วินาที แสดงวง progress เลือกข้อความฉุกเฉินสำเร็จรูปและแก้รายละเอียด
- ระบบขอสิทธิ์กู้ภัย เอกสารประกอบ Admin อนุมัติ/ปฏิเสธ แจ้งผลและประวัติสิทธิ์
- ประวัติ SOS/เคสที่รับ และกรองเคสเก่าจากรายการปัจจุบัน
- โปรไฟล์/รูปประจำตัว เปลี่ยนอีเมล/รหัสผ่าน ลบบัญชีด้วยตรวจรหัสและยืนยันซ้ำ
- ธีมมืด/สว่าง ค้นหาแชท กรองยังไม่อ่านและซ่อนแชทเก่า
- บริการรับข้อความเบื้องหลัง/notification, reconnect และ wake/Wi-Fi locks
- เข้ารหัส end-to-end ของ private routed traffic, key pinning, signed rescue identity, hash verification และ account isolation

ส่วนเสริมเหล่านี้ไม่ขัดโจทย์และหลายส่วนช่วยงานฉุกเฉิน แต่การอนุมัติกู้ภัยและหน้าจอประวัติเพิ่มขั้นตอน จึงควรให้แชท/SOS ที่หน้าแรกเข้าถึงง่ายและไม่ต้องผ่านงานสมัคร/คลาวด์ก่อน

ข้อสรุป: มี implementation ครบกลุ่มฟังก์ชันหลักและมีผลอัตโนมัติรองรับ แต่ยังไม่ควรระบุ “ผ่านโจทย์สมบูรณ์ 100%” จนเติมความชัดเจนสถานะส่ง SOS และมีหลักฐาน field test / live backend ของรุ่นล่าสุด
